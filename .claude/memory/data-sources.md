# Data sources: reading, holding, refreshing

## One owner per source; renders never fetch

Each shared source has one owner that schedules its reads: git state, PR lookups, tmux pane names, plugins' session files, today's transcript scans, the auto-compact setting, the cache expiry and the host's name and user. The host name has a period because it follows the network and a daemon lives for days; the user shares it, because a lookup that failed (a directory service briefly away) must be tried again. A read returns the stored value, and only a value that has never been read is awaited. Refreshes come from triggers (a watch, a period), never from a render. A pushed frame does no I/O at all. It draws what the owners have stored.

A render request waits for what its arrival started: the refreshes it triggers, the first value of every keyed source its view declares except two, and every run of its session's or its directory's sources that answers a key the source has no answer under yet: a first value, or a key or dependency that moved. A period's or a watch's re-read is not waited for, since it keeps the answer it has standing, and another session may have started it. It waits only until its client's deadline, less what the draw needs, and whatever has not answered then is drawn as pending. The client states the deadline because only the client knows when it hangs up: the native client counts its budget from before it connects, the Node client from after, and under load the daemon reads a request late. A config's first request compiles in its arrival turn, and that compile can spend the whole deadline, so the first bar from a new directory or config can be mostly pending. A frame waits for nothing, and anything not answered yet is drawn as pending.

The two exceptions are today's day sums and the branch's PR. Both are slow and outside the daemon (a scan of every transcript under the directory, a forge's network call), and every bar reads both, so waiting on them would make every first bar as slow as the slowest. They draw pending and land through the store they are read from. The request still waits for its own session's refresh, which is one transcript.

A value the daemon itself made stale (a click's move) is pending too, but no request waits on it: the move may take as long as the program it ran, and a wait for it would end at the deadline with the bar from before the click. So a pending value says whether its key was never answered or was superseded, and a request waits only on the first.

A supersede holds back every other trigger of its key until it resumes, and overlapping supersedes need every resume, so no read that ran during a move stores the world from before it.

A stored value changes only when a read finds something different, compared by structure. Every stored value is something a feed wakes on, so a period that rewrote an equal value would wake every feed showing it once a period.

## Periods run only while something holds the key

Each session view declares the built-ins and sources its config can reach, and every key its request names for them: which repo, which pane, which plugin session file, which Claude Code directory. Those declarations are the holds. The reach is walked over every preset, not the picked one, so a preset switch moves no hold. A built-in no preset reads takes no hold and runs no request refresh, and the forge lookup runs only for a config that reads a PR field. A per-session fold a config stops reading keeps its state and resumes from it when declared again. A period runs only while its key is held. It measures from the last read that landed, and resumes where it left off. Each source's LRU evicts only unheld keys, and a daemon with no subscribers keeps no timer and makes no external call.

## Where a variable lives

Variables that read anything per session live in each session's view: inputs, state, templates, time, and every shell or file source. A source is the view's whatever its policy reads, because what it read reaches a session only through that session's facts document, and a node every session in a directory shares could read no one session's document. Everything else lives in the directory's store, however many sessions render there.

A shell or file source's run belongs to neither: its identity is a digest of what the run needs (the read, the parser, the normalised policy, the hash of the key's value) and nothing the renderer owns, so one daemon-wide owner runs each identity once for every view that declares it. The facts arm a view follows holds the run; the view holds only its declaration of it. A pending reading is never written into a variable's node, which is what keeps a moved key's old value on the bar until the new run lands. A ttl period measures from the last landed read, as every source's does, so a run that timed out waits a whole period from its failure.

## Git

Git state is keyed by repo root, not by cwd or session. Two things refresh it. One is a watch on HEAD, the index and the branch refs tree of the common git directory: a linked worktree's own git directory holds no refs, and a branch name's slashes are directories, so a watch one level deep hears neither a worktree's ref move nor one on a slash-named branch. The tree stops at the branch refs because on Linux a recursive watch costs one watch per entry, and remote refs and tags are the remote's to grow. The other is a period over held repos, which also catches working-tree edits no watch sees and events a filesystem drops. A directory watch binds an inode, not a path, so a git directory removed and recreated at its path (a worktree removed and added again under the same name, a re-clone) is deaf to the watch opened on it, with no event to say so. The watch's key is therefore the directories it bound, every pass derives it again, and a new key rebinds, so a recreated repo is heard within one period. Following the git directory through its parent instead would not do: the last worktree's removal deletes the worktrees directory too, and a parent watch on macOS delivers the whole working tree's events. A watch that fires mid-read queues exactly one re-read after it, so the last change always lands. A change in a repo nothing uses reads nothing until the repo's next use. A directory resolves to its repo only when a view declares, so drawing a frame never resolves anything.

## PR lookup

The forge lookup is a separate source on the repo, and a git refresh never awaits it. Its key is the branch plus the remote, so a branch switch or a re-pointed origin starts a new key. Each key keeps its last answer, so switching back to a branch answers from that branch's own lookup. The lookup period is longer after a success than after a failure, and a key whose lookups keep failing is retried at a doubling interval up to the success period, so a forge that is down costs one spawn per success period per key. At most a few lookups are out at once across every repo, because each is a spawned CLI over the network and a daemon holding many repos would otherwise start one per repo in the same turn. A branch's PR is its newest in any state. A merged or closed PR still counts only while HEAD is its head, because the forge matches by branch name and branch names get reused. A failed lookup shows as a visible error, distinct from "no PR" and never as a missing value.

## Not answered yet is its own state

A value is pending (not answered yet), absent (the domain has nothing), failed, or ok. Reading a pending value throws a pending signal. Every place that evaluates a template treats that signal as its own outcome, never as a failure. No error is recorded and no default is used, since a default stands in for a failure, not a wait. A pending placement draws loading cells laid out like the last frame drawn from the same source, so the bar doesn't reflow when the answer lands. A cell wider than its line is the exception: a placeholder's blanks hang at a break, so it draws one line and the bar shrinks until the answer lands. A pending globals rule keeps the name it last settled on.

Pending is a plain value recognised by its discriminator, so it survives a process boundary. A source's own JSON can spell the same thing, so a path walk stops testing for pending once it steps into a source reading's value: a file that says `{"kind":"pending"}` is a value.

An input variable stays pending until its view's source is bound and answers its path. Its default answers only a payload that lacks the path, not a missing payload. A cache policy reads its source when the value it keys on first answers, not at declaration, so a view's source reads once when the view opens.

## The facts document

Each session's view follows one facts document through the facts source, and the payload a template reads is composed from it, so the two cannot disagree about what an owner holds. Every declared built-in and every declared source has a key in it, and nothing else does. A read of a built-in that has no key is undeclared, a value of its own beside pending: it throws naming the fact, no default answers it, and its segment draws ⚠. A blank there would hide exactly the walk's miss that a declaration risks. A stamp is the instant an answer first differed from the one before, so it is taken in a reaction's effect, never in a derivation: a derivation that read the clock and its own prior answer would answer by when it ran.

The facts source is one interface over arms, and nothing above it knows which arm it has. The in-process arm is the one the daemon and the demo run on: it takes the view's holds on the owners and assembles the document from what they hold. The recording arm serves the last document the replay's walk over the file reached. The file's order is the only order a recording has, never its instants: a document can be stamped in the millisecond after a draw read the one before it, and under a held clock a request, what lands in its wait and its answer share one instant. A recording holds one session and refuses a follow of another by name, because a pending that will never land is a void. The seam is proved by a replay drawing what the live renderer drew with nothing read and nothing spawned after the load. A provider read put back on the draw path fails that test because the replay's owners hold nothing, so the frame it draws differs from the live one; a read that reaches a file or a process is counted besides, but the frames are what catch a read served from memory. Each draw line carries what the session's clicks and menus left for that draw: the session store's values and its revision, the histories' depths and when its menus' idle period began. The revision crosses as itself because the draw reads it (a frame keeps the last frame's memory only while it holds), so a replay that minted its own would fade where the live bar did not. The idle instant is the one the draw was handed: drawing a menu's first frame moves the clock, and a click moves it without any frame, so a replay cannot rebuild it from its own frames. A shell or file source's run crosses in the documents, so a replay runs nothing. A run no document from the reached line on holds is that source's failure, naming the run, never a pending that will not land: the replay's config declares a run the live one did not, edited since or across a save. A draw line carries what the draw was handed (who it drew for, each lane's feed, the diagnostics list), so the replay draws the door's indicator, the open viewer and the lane toggles from what the live draw read. A lane's frames draw through the same view as the answers and write its frame memory and the session's effect memory, so they cross as draws too, and the replay draws them in the file's order, each at its own instant, which falls between whole milliseconds. What a recording cannot carry is the config, so a recording across a save or a hand edit replays every frame against the one file the demo is given.

A recording opens on the turn the bar is drawn from, and writes that turn again wherever its hold moves. A turn whose inputs cannot be read holds the bar on the last turn taken, whose request and picks the session has since moved past. No line beside the draws can rebuild it: a click moves the picks between draws without writing a draw line, and the replay's turn resolves its picks from the one store the draw's `state` variables also read, so it would need two sets at once. So the replay takes each turn line's turn and holds its own over the same lines, by making its turn inputs fail as the live ones did.

A document's runs are the ones its session's state keys declared, so a recording writes the clicks' state ahead of any document stamped after the state moved, and a replay restores it there. Restored only at the next draw, the replay reaches the document still declaring the old key's run, which no later document holds, and draws that source failed where the live bar showed its old value.

A recording written out of the daemon follows the session's current view as the render cache holds it, and moves when the cache's entry for the session changes. It never follows a follow: a follow is taken before its view opens, and a successor is opened before the old view retires, so recording every follow writes documents no bar drew and interleaves two sequences the replay cannot tell apart. An answer is drawn after its request's wait, at the request's instant but from what the view took during the wait, so a draw line is written when the answer is drawn, after the document that draw read. A draw reads three things of the view its request holds, its turn, the document its follow holds and the request it is declared with, and each is written again before the draw line when it is not the last of its kind the recording wrote: the session may have moved to another view during the wait, and a later request has declared that one. A hold is a view's and the replay holds one view, so a draw of a view the session moved away from goes between that view's turn and the current view's, and every line follows the turn of the view it came from. The document is the follow's, not the turn's: a held turn keeps an older one, which the replay's held turn keeps by itself, while the run lanes read the follow's. Two requests of one session can wait at once, and a replay takes arrivals, declarations and draws in the order the file has them. An answer goes only to the recordings that saw its request arrive, because a recording started during a wait has no line for that request, and a draw of it would make a file its own parser refuses. A lane's frame answers no request, so it goes to every recording of the session. The header carries the home the payloads were composed against: a replay on another machine would otherwise name its own home as `~`.

A request's refresh and the wait for what it started go through the view's follow, so the request path holds no owner; a recording starts nothing and waits on nothing. The stamps live on the view's follow, so a rebuilt state or the idle sweep restarts them, and a document's instants mean first seen by that view. The update is the exception: one fact for the daemon, stamped by the watch that owns it and shared by every session's document, so one change has one instant everywhere.

The `today` fact holds sums, never a day's total, because the day turns over at midnight with no owner moving: a draw picks its day out of the fact by its own instant. It carries both inputs of that pick, the directory's day sums and the rendering session's own days, so the projection is a pure function of the document. The session's days are in the fact only when its transcript sits outside the directory's projects; one under them is already in the sums, and counting both would double it, so its own days stay empty and its ingests do not move the fact. The session's last ingest failing makes the whole fact failed, because a total silently missing the session's own work is a confident wrong number.

The document, what the payload is composed from beside it, and the globals a draw builds its options from are taken together as one turn, in one reaction, and the payload, the globals and the document are all read off that one value, so a draw never mixes a document with a request or a pick it was not composed from. A turn that cannot be taken, or a document its source could not restamp, keeps the last one and sets a failure the draw reads, so the bar says in its ⚠ indicator that it is drawn from older facts; a log line alone would reach nobody. The source logs its own fault once when it sets it, and the turn logs only a turn that failed, so a fault that persists is one line.

## Usage and today

Per-session usage records live in one store. Session totals and today's total are folds over that store, and nothing scans the transcript tree per render. Today counts the rendering session plus every record whose transcript sits under that Claude Code directory's projects. It doesn't count every session the daemon has seen, because that sum would change depending on which other sessions happened to render. Today's period rescans the tree, so sessions that never render (headless `claude -p`, the Agent SDK) and sessions whose config reads no usage fact, which ingest nothing on their own ticks, still reach today within a minute. Today rolls over at local midnight without a refresh.

A transcript's change stamp is its mtime plus its size, because an append within one mtime tick changes only the size.

## Transcript folds are incremental

A fold keeps a byte cursor and running sums for each file and reads only the bytes appended since its last read. It reads in bounded windows of whole lines, so a cold fold of a huge transcript holds one window in memory, not the whole file. Reads go through a small gate of slots, however many folds are queued, and a cold fold takes a slot once per window. A session's fold is one in flight at a time, and a request arriving during it takes its answer, because the gate bounds what reads at once, not what is asked for: were every request to start its own fold, a population of cold sessions would ask faster than the gate finishes, no fold would land, the stamp fast path would never engage, and every refresh would wait in the queue. A rewrite re-folds that file from zero. A rewrite shows up as an inode change (a rename-based /compact, log rotation) or as the file shrinking below the cursor (in-place truncation). A missing transcript is an empty fold, not a failure; a transcript that has to be read and cannot be is a failure with its reason, never an empty fold. A fold whose stamp still matches is served as it stands without a read, whatever the file's permissions now say. The change stamp never tells missing from unreadable: an empty stamp only means "not a hit", and the read is what classifies, so the stat must not grow a second classification beside it. Metrics and activity keep their own cursors over the same bytes rather than sharing the usage store's read, so the store's cursor and sums always change together.

## Activity: the turn boundary is a prompt

Activity facts come from message content, which the transcript parse otherwise drops, so they are reduced to bounded scalars at the one parse site. The turn boundary is a human prompt, recognised from the marks Claude Code writes. An entry with a non-human origin is another turn of the same prompt. The interrupt marker, built-in command tags, local command output, shell command tags, meta entries and compact-summary entries are not prompts. An entry with no mark at all is a prompt, so SDK input and older Claude Code versions (which write no origin) still count. Per-turn facts reset only at a prompt, the todo list never resets, and an interrupt clears only what was running. Tool call ids are kept only to pair a result with its call, and they never cross into the payload.

## File-event delivery is one fact

A watch the OS has stopped feeding reports nothing, exactly as a folder nobody writes does: macOS's fseventsd can wedge after days up, and then no directory watch in any process hears anything, with no error. Every directory watch in the daemon rides one FSEvents stream on macOS, or one inotify queue on Linux, so delivery fails for the whole daemon at once, and one owner judges it for every watch. Only writing tells a dead watch from a quiet folder, so that owner rewrites a probe in a folder of its own each period. The config's folder is the user's, a project's is a repository, and the state directory itself is written by the log on every request, so none of them can hold the probe. Two probes in a row unreported is a stall. One is not, because libuv's macOS watch drops what lands while it rebuilds its one stream, which any watch opening or closing in the daemon makes it do. The probe folder's identity is judged before delivery, because a folder replaced at its path never reports a probe to the old inode's watch. The same period judges every directory watch in the daemon against the disk, reopening one whose path holds another folder and opening a deaf one again: a strict ancestor renamed away and another tree put at its path reports nothing to the handle bound under the old one, and a refusal the OS has lifted is heard only by a retry. A reload that keeps its watch retries nothing, because one that did would answer the failed window its own handle's error told. A refused or failed watch, the folder gone or replaced, or a probe that can't be written leaves the daemon unable to check, and that reads as neither delivering nor stalled. The probe is a period on the watch's health, never on reads: re-reading on a timer would hide a sick fseventsd behind a bar that looks alive.

An edit made while the daemon can't vouch for delivery may never have been heard. So the span opens at a stall or at the move into unable-to-check, only an event the watch reports closes it, and closing it re-reads every config, every held plugin file and every source a config watches a file for, however the span ended. The bar's row stands for as long as the span is open, so a probe that lands but is not yet heard still warns.

While file events are stalled, every `watch_file` variable carries the stall as its standing fault, read from the delivery owner, so the value says it may be stale. Every move of delivery re-reads them as a catch-up does, because a stall can end in unable-to-check with no catch-up to come, and no variable may drop the fault without reading again. The fault follows the stall and not the span, because unable-to-check is no finding about delivery: faulting on it would mark every variable for the life of a daemon whose watches may be hearing everything. The bar's row carries the rest of the span.

## Plugin storage

One daemon-wide owner reads every plugin's session files. A plugin source has no period: its folder's watch is its only trigger, so a folder that can't be created, a refused watch, one that errors on a folder still there, or a folder that can't be stat'd, is a standing failure of every source in the folder, never a silent stale value, and never the whole config's failure, since one plugin's folder must not take down the bar. A refused or erroring watch, or a failed stat, stands only while the OS gives that answer: the delivery owner's period asks again (the registry reopens a deaf watch, the owner judges the folder), and the failure clears when the answer changes, in the same generation. Only a folder that can't be created waits on a reload, since the key request's mkdir is its only retry. The owner compares the watch's deafness only when a window closes, never on a period, because the registry's reopen and the owner's judgment are two listeners to one period in an order nothing owns, and a watch that errors after every reopen listens for an instant between them; this holds because the registry tells a window on every change of deafness, deaf to deaf included. With no period, nothing visits an entry while no view holds it, so a hold returning to a kept entry re-reads it, drawing the kept value meanwhile; otherwise a file written while a session was away never reaches its bar.

While file events are stalled, every plugin source reads the stall as its standing failure. A stall doesn't move a generation, because a reload opens a new watch on the same stalled service. A folder found lost while stalled keeps reading the stall until delivery resumes, for the same reason: the reload that would move it on rides that stalled service, so a file read once from the path would freeze there unreported. Every period still judges each folder against the disk, because the event naming a removed folder and the follower's event that reloads its config ride one stream, which can drop both at once without a stall.

A folder's watch is held by what declares the folder, never by a view, because opening or closing a directory watch leaks on macOS. A folder is keyed by its path and a generation the owner moves on every loss, because an install replaces folders by rename and ext4 reuses a freed inode number; birth time sits beside device and inode in a folder's identity for the same reason, where the host supplies one. A host without statx copies ctime into birth time, and a directory's ctime moves on every child write, so a copy makes each write read as another folder: identity there is device and inode alone, which misses only a folder made again on a reused inode. An event naming the folder itself is checked against the disk, because a chmod, a utimes or an xattr reports the same name as a removal. A removed storage folder recovers by reloading the config through the watch that already follows the plugin's folder for its definition, because a lost generation stays lost even after its watch has moved onto a folder made again at its path: the reload's build recreates the folder under a new generation, and a spurious fire reloads into the same key and opens nothing. Until the reload, a lost folder's held files are re-read from the path, so no draw shows a value from a folder that is gone; while its watch is deaf they read the deafness, as they read a stall, because a file read once from a path no watch hears would freeze there unreported.

Only the daemon's storage owner creates, watches or sweeps a storage folder. A build outside the daemon, such as the doctor's or the demo's, holds none of the daemon's sessions, so a sweep there would remove files they hold.

## Auto-compact window

The window changes only when someone types /autocompact in the session. It is read back from Claude Code's user settings in the session's Claude Code directory, and re-read only when that file's stamp changes. The file is user-global, so the value isn't per session. It's unverified whether other running sessions pick up a change.

## tmux

The pane comes from the client's hint. The daemon's own TMUX and TMUX_PANE are never read. A slash click types into that pane, so every bundled slash control is gated on the session being in tmux.

docs/segment-authoring.md walks through it, and its snippets run in CI. A built-in segment is authored the same way against the bundled default. The one difference is the data source: a provider fills it into the payload, and input variables read it.
