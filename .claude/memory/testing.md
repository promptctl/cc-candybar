# Testing

- Read rendered bytes through the test helpers' ANSI reader, not a regex of your own. Every link carries an id= derived from its URL, so a regex that spells out ESC]8;; matches nothing.
- Jest runs ESM through ts-jest. If an ESM dependency ships untranspiled, add it to the transform allow-list under both node_modules/<pkg> and pnpm's .pnpm shadow path.
- The transform transpiles only, so a type error in a test passes jest and fails the typecheck. Types have one checker, tsc, which the Test job runs before the suite; checking them in the transform costs seconds per file on CI's cold cache.
- Tests time out at 30 s. Fake time and the filesystem rather than waiting on real ones.
- A wait on a real process or a watcher goes through the shared poll helper, never a private loop that answers false at its deadline: the helper names what never held. Its budget is a real sleep rather than a deadline read off a clock, so it keeps working under jest's fake timers; a clock faked outside jest's sandbox freezes it.
- A directory watch has no ready signal, and a write that lands before it is live is never reported, so a single write proves nothing about a watch until the watch has delivered an event: the write is re-applied through the shared retry helper until the event it waits for proves the watch live. A sleep before the write is a bet on when that happens. Its rounds are the poll helper's waits, so it rides no timer a test could fake. A condition over a count that a later event can still move is at-least, never exact. A latency is timed on one write made after another value has proven the watch live, never on a re-applied write, whose answer may belong to an earlier round. A re-applied removal emits nothing once the path is gone, so each round lays it down only when it is missing, and the first round stays the bare removal under test: rewriting a file before removing it is a change event, which a watch can hear in place of the removal.
- A truncating write leaves the file empty between its two steps, and a read that lands there is a change of its own. A test that counts a source's changes or frames rewrites the file through the product's atomic write, which renames the new contents over it.
- A file written under jest's fake timers carries the real clock's mtime, so a check that ages a file against Date.now() reads two clocks and drifts with the machine's load. Pin the file's mtime to the fake clock before anything reads its age.
- Test setup isolates the daemon from the host. Claude Code's config directory points at an empty dir, so no test reads the host's Claude Code settings or transcripts. The registry URL points at a closed port, and managed settings at an empty dir.
- A daemon-backed test runs in the jest worker through the harness, over the connection a socket gets, and a real process is for a test whose subject is the process. The daemon reads its paths when it writes, so the env a spawned daemon would be given, whole, is the test file's own until the stop, and what is logged by then is drained before that env goes back.
- A click's write reloads the config inside the click, so a render after a save proves nothing about a watch: it passes with no event delivered. A proof of a watch is an edit made with no click.
- A harness stop does not wait for a closed daemon's work, because nothing says that work has settled, and a count of children reads zero between one pass's launches. That work launches through its own daemon, so it is refused whichever daemon is live, and the refusal is in that daemon's stats: that count, not the children, is the fact to wait on. A line it logs after the close says so and can land in the next daemon's log, so a reader of a daemon's events anchors on where the event starts.
- The env in a jest worker is a copy, so a daemon placed there is placed for what reads that copy and nothing else: the home and temp directories and the time zone stay the host's. A case that places those keeps a real process.
- Every directory test setup mints is named for its worker's pid, because a global teardown can run while another run's workers are mid-file, and a daemon in a worker holds no lease to show it is alive. A pid the sweeping process owns is its own finished run, since jest ends its workers first.
- Test setup also isolates the state directory, so a test never sees the host's answers for repository configs. A test that loads a project or cwd config, or a repository's plugins, approves the directory first through the approval helper. Unapproved, the layer is silently absent from the chain, and the failure looks like the config never loaded.
- Test daemons watch the Jest worker's pid and shut down when it dies, so a killed or timed-out Jest can't leave an orphaned daemon.
- A process the daemon spawns leads its own process group, so a signal to a test daemon never reaches it, yet it dies with the daemon, SIGKILL included, by the daemon's lifeline. A stub that blocks waits on a connection the test holds, never on a pipe it holds itself, so the test's teardown, or the worker's death, ends it however it was started. The update act is the exception: it outlives every daemon by design, so a stub standing in for it must end itself, for example once the test's scratch directory is gone.
- To show nothing is left running, read an async-hooks set of live resources, not the active-resources list: that list omits what is unref'd, which is nearly every timer the daemon holds. Put real work in the path first and assert it got there: a lane subscription refused because the lane is off is no feed, and a close test over it passes with the close removed.
- Close any render cache a test builds. Otherwise its idle sweep keeps it, and every compile it serves, alive for the life of the worker.
- The authoring docs under docs/ are tested against the live loader, so editing a doc can fail tests.
- In a worktree whose node_modules is a symlink to the main checkout's, pnpm can refuse to run scripts. If it does, run the binaries in node_modules/.bin directly.
- A render request answers by its client's deadline, so a first render from a new directory or config can draw sources as pending. The e2e render helper asks again until the request's own render event says nothing drew pending, as Claude Code's next tick would. A case that means to see the pending answer sends one request of its own over the wire.
- The load gate and its feed criterion are judged on CI's runner, not on a busy Mac. When fseventsd falls behind, the kernel holds file writes back, so the daemon's log writes occupy the libuv pool and the transcript reads behind them miss their deadlines while every draw stays fast. The numbers are then the machine's, not the daemon's.
- The suite's time is judged on CI's runner, from the per-file durations in its Test log: two cores run four workers, so a CPU-bound file is far slower there than locally, and a loaded Mac fails the watcher tests outright. The wall is bounded below by the longest file, and parse plus compile of the bundled default is the cost most rigs pay once per test, so a sweep over render options renders one rig rather than building one per point.
- A heap snapshot of a Jest worker costs seconds, because the worker's heap holds every transpiled module of the suite. A test that needs snapshots takes them in a bare child process.
- A colour check that walks the whole theme registry AND takes far longer than any test in the suite is a nightly audit, not a test: it runs on GitHub's schedule only, never locally, on a PR or on a push to main, and nothing is gated on it. Walking every theme alone does not make one; the suite keeps the registry walks that finish in seconds.
- The benchmark reports latency distributions beside the machine, node and build they came from, and judges none of them. A number compared across machines, node versions or sample scales says nothing, so a baseline join says how the two runs differ before it prints a ratio, and the header says when the machine ran more work than it had cores. Its wire group drives the built bundle and refuses one built from other source.
- A benchmark sample is vouched for by what produced it, because a fast sample that drew an error or nothing is the failure that looks like a win. In-process draws report their failures instead of throwing, so each crosses a checkpoint. A warm tick is held to the daemon's own record: its render event drew clean and its counters show no cache entry built and no request erred. The daemon logs whole milliseconds, so the client's round trip is the headline and `took` is the daemon's coarse view.
- A tick the client gave up on may never have reached the daemon (a connect that timed out) or may still be running in it, so a benchmark never counts events one-for-one with ticks across a failure. Settling matches an answered tick to the last event logged since the tick began; a straggler from an earlier tick is older and drew more pending, so it can delay a verdict and not forge one. A measured run with any failed tick leaves the daemon-side series out, because a count cannot say which event is a straggler's.
