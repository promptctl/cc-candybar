# Testing

- Read a draw from the frame it returned, never from its bytes: only a test whose subject is an encoder reads bytes. Two draws are two objects and each frame carries its own wall-clock moment, so compare their rows. A comparison by identity passes whatever was drawn, and a whole-frame equality can fail on the clock. A frame in a template string compiles and prints nothing useful, so a failure message hands over its text.
- Jest runs ESM through ts-jest. If an ESM dependency ships untranspiled, add it to the transform allow-list under both node_modules/<pkg> and pnpm's .pnpm shadow path.
- The transform transpiles only, so a type error in a test passes jest and fails the typecheck. Types have one checker, tsc, which CI runs as its own check; checking them in the transform costs seconds per file on CI's cold cache.
- Tests time out at 30 s. Fake time and the filesystem rather than waiting on real ones.
- A wait on a real process or a watcher goes through the shared poll helper, never a private loop that answers false at its deadline: the helper names what never held. Its budget is a real sleep rather than a deadline read off a clock, so it keeps working under jest's fake timers; a clock faked outside jest's sandbox freezes it.
- A directory watch has no ready signal, and a write that lands before it is live is never reported, so a single write proves nothing about a watch until the watch has delivered an event: the write is re-applied through the shared retry helper until the event it waits for proves the watch live. A sleep before the write is a bet on when that happens. Its rounds are the poll helper's waits, so it rides no timer a test could fake. A condition over a count that a later event can still move is at-least, never exact. A latency is timed on one write made after another value has proven the watch live, never on a re-applied write, whose answer may belong to an earlier round. A re-applied removal emits nothing once the path is gone, so each round lays it down only when it is missing, and the first round stays the bare removal under test: rewriting a file before removing it is a change event, which a watch can hear in place of the removal.
- A truncating write leaves the file empty between its two steps, and a read that lands there is a change of its own. A test that counts a source's changes or frames rewrites the file through the product's atomic write, which renames the new contents over it.
- A file written beside a held clock carries the real clock's mtime, so a check that ages it against the clock's `now` reads two clocks and drifts with the machine's load. Pin the file's mtime to the held clock before anything reads its age.
- A test states the machine it runs on by handing the code a host over an environment it names, and never writes the worker's: that environment is one ambient value every later test in the file inherits. A lint rule on the tests fails a write, apart from the setup files, the in-worker harness and a stub put on the path. A child a test launches inherits the environment of the launcher it was given, less the variables scoped to a repository, so a test that means a child to see one sets it in the launch's overlay.
- Test setup isolates the daemon from the host. Claude Code's config directory points at an empty dir, so no test reads the host's Claude Code settings or transcripts. The registry URL points at a closed port, and managed settings at an empty dir.
- A daemon-backed test runs in the jest worker through the harness, over the connection a socket gets, and a real process is for a test whose subject is the process. That test lives in the process tier, and nothing else needs a build. The harness reads the env a spawned daemon would be given, whole, once when it builds the daemon, so a case places the env before the build, and the stop drains what is logged and ends the log before the next daemon opens that file.
- A click's landing hands the renderer the configs it moved inside the click, so a render after a save proves nothing about a watch: it passes with no event delivered. A proof of a watch is an edit made with no click.
- A harness stop does not wait for a closed daemon's work, though the value of its close says when that work has settled, and a count of children reads zero between one pass's launches. That work launches through its own daemon, so it is refused whichever daemon is live, and the refusal is in that daemon's stats: that count, not the children, is the fact to wait on. A line it logs after the close says so and can land in the next daemon's log, so a reader of a daemon's events anchors on where the event starts.
- The env in a jest worker is a copy, so a daemon placed there is placed for what reads that copy and nothing else: the home and temp directories and the time zone stay the host's. A case that places those keeps a real process.
- A held clock belongs on a daemon its case owns, and that daemon's clients state their deadlines on it. A request's budget is its deadline less its arrival, so a client on the wall clock beside a held daemon gets a budget that is wrong by however far the two have drifted, and a warm render hides it by having nothing to wait on.
- A held clock holds a request's wait and backstop too, so a held daemon's request answers when its work does or when the case advances to its wait's end. A case that wants a source to outlive a deadline has to advance, and stops at that end: an advance fires its timers in one turn, so one past the backstop as well answers with the daemon's timeout reply before the render can draw. A held daemon freezes everything the daemon builds: frames, sweeps, debounces, file-event periods and menu idle all wait for an advance. What the adapters build (a launch's timeout, the log, the memory backstop, the lane edge, session-state's debounce) runs on the machine's clock and stays on real time, because a real child or file lives there. A timer already due, and a deferred run, wait for the next advance, even by 0: the held clock takes no turn of the real loop. Work that holds the loop (a slow render) is time the case burns, never real time: a burn moves the clock without firing anything, so what fell due runs late at the burned moment on the next advance, and a repeating timer runs once, as an interval does.
- A wall-clock bound as tight as the draw's reserve stays on a real process. On CI's runner a cold draw in a worker ran well past that reserve, where process runs on that shared runner come within a few milliseconds of it, and a Mac reads the two alike, so a local comparison cannot clear the move.
- The request backstop answers only if the loop gets a turn before the reply, and a synchronous compile outlasting it does not give one. In a worker the reply won or lost by which case ran before it, and on CI won even with a source still running, so a case that needs the backstop to win stays on a real process. There the render is held by something that cannot finish on its own, never by a heavy config: slow compiles bet on the runner's speed, and a fast runner finishes inside the limit.
- A clock that stands still cannot prove a request samples it once, because every read agrees. A case about that one sample stays on a moving clock.
- A memory end finishes only once its peer has read to the end, so a client that never reads never has an answer delivered, half-close or not. A case that means a client is gone reads what it is sent, or it passes for the wrong reason.
- Every directory test setup mints is named for its worker's pid, because a global teardown can run while another run's workers are mid-file, and a daemon in a worker holds no lease to show it is alive. A pid the sweeping process owns is its own finished run, since jest ends its workers first.
- Test setup also isolates the state directory, so a test never sees the host's answers for repository configs. A test that loads a project or local config, or a repository's plugins, approves the directory first through the approval helper. Unapproved, the layer is silently absent from the chain, and the failure looks like the config never loaded.
- Test daemons watch the Jest worker's pid and shut down when it dies, so a killed or timed-out Jest can't leave an orphaned daemon.
- A process the daemon spawns leads its own process group, so a signal to a test daemon never reaches it, yet it dies with the daemon, SIGKILL included, by the daemon's lifeline. A stub that blocks waits on a connection the test holds, never on a pipe it holds itself, so the test's teardown, or the worker's death, ends it however it was started.
- To show nothing is left running, read an async-hooks set of live resources, not the active-resources list: that list omits what is unref'd, which is nearly every timer the daemon holds. Put real work in the path first and assert it got there: a lane subscription refused because the lane is off is no feed, and a close test over it passes with the close removed.
- A home a test opens over a real owner is closed by the case that opened it. A held entry's period re-arms after every read, so an open home ticks for the life of the Jest worker, and the file it fails is a later one that counts the worker's timers: a daemon close case then reports leftover periods that its own daemon never armed. Entries held together re-arm together, so that failure lands only when their period's turn falls inside the counting case. Run a suspect file alone before blaming it, because a file run after a leaker counts the leaker's re-arms. A disposed registry still reports its subscriptions, so whatever holds lanes over one ends with the registry's own teardown, not beside it.
- Close any render cache and collector a test builds. Otherwise the cache's watchers and the collector's sweep keep them, and every compile they serve, alive for the life of the worker.
- A fake owner makes a key's first read in its declaration, as a real owner's declaration takes its entry. A request's wait redraws when a later world state reaches the renderer, and a derivation that reads a key an observable map does not hold yet tracks only the key's presence: if the read stores the key there, the landing later changes a value the draw never subscribed to, and the wait hangs to its deadline. A test's own wait for its runs to finish is wider than a request's, since it also covers a key that moved under a standing value, which a draw owes nothing for.
- The authoring docs under docs/ are tested against the live loader, so editing a doc can fail tests.
- In a worktree whose node_modules is a symlink to the main checkout's, pnpm can refuse to run scripts. If it does, run the binaries in node_modules/.bin directly.
- A render request answers by its client's deadline, so a first render from a new directory or config can draw sources as pending. The e2e render helper asks again until the request's own render event says nothing drew pending, as Claude Code's next tick would. A case that means to see the pending answer sends one request of its own over the wire.
- The e2e click helper sends a click again on TIMEOUT, as the render helper does, which is safe because a TIMEOUT to a click means its action did not run (architecture.md). It learns what became of a click from the answer, never from the log. A held clock runs a deferred turn in the advance that queued it, so a case that writes a click's frame and advances in the same turn sees the guard answer ahead of the frame. It cannot show the frame being read first, as the loop does when it was already waiting on the socket; that order is checked over a real loop turn (the connection test and the timekeeper test).
- The suite's time is judged on CI's runner, from the per-file durations in its Test log: two cores run four workers, so a CPU-bound file is far slower there than locally, and a loaded Mac fails the watcher tests outright. The wall is bounded below by the longest file, and a rig built through the shared rig builder pays parse plus compile of its source once per file, so a sweep over render options builds its rigs there and draws each point.
- A test of what the client makes of an answer or of a malformed frame runs the round trip over an in-memory connection on a held clock, or hands the wire answer to the translator. A real socket under the statusline's own 50 ms budgets is a bet on the worker's loop, and a wider budget only makes the bet longer.
- Load made to reproduce a flake competes with the live daemon on the same machine, whose clicks then answer with its timeout reply. Reproduce a loop stall by blocking the loop in the test's own process; a burner outlives an interrupted tool call, so bound it with `timeout`, and heavier load belongs on CI.
- A heap snapshot of a Jest worker costs seconds, because the worker's heap holds every transpiled module of the suite. A test that needs snapshots takes them in a bare child process.
- A colour check that walks the whole theme registry AND takes far longer than any test in the suite is a nightly audit, not a test: it runs on GitHub's schedule only, never locally, on a PR or on a push to main, and nothing is gated on it. Walking every theme alone does not make one; the suite keeps the registry walks that finish in seconds.
- The benchmark reports latency distributions beside the machine, node and build they came from, and judges none of them. A number compared across machines, node versions or sample scales says nothing, so a baseline join says how the two runs differ before it prints a ratio, and the header says when the machine ran more work than it had cores. Its wire group drives the built bundle and refuses one built from other source.
- A benchmark sample is vouched for by what produced it, because a fast sample that drew an error or nothing is the failure that looks like a win. In-process draws report their failures instead of throwing, so each crosses a checkpoint. A warm tick is held to the daemon's own record: its render event drew clean and its counters show no cache entry built and no request erred. The daemon logs whole milliseconds, so the client's round trip is the headline and the daemon's logged duration is its coarse view.
- A tick the client gave up on may never have reached the daemon (a connect that timed out) or may still be running in it, so a benchmark never counts events one-for-one with ticks across a failure. Settling matches an answered tick to the last event logged since the tick began; a straggler from an earlier tick is older and drew more pending, so it can delay a verdict and not forge one. A measured run with any failed tick leaves the daemon-side series out, because a count cannot say which event is a straggler's.
- A quarantined case is counted pending by jest while its failure stays in the result, so a reporter or record that reads `status` alone undercounts failures. The failure signal is `failureMessages`; the quarantine mark in it says the gate let it through. A file that names its own environment runs outside the quarantine's, so a line for it would be accepted and never honoured.
- A jest reporter and the records module it uses load untransformed, so they are CommonJS. A result exists only for a file that ran, so a lost file is the gap between the files jest scheduled (counted after -o, sharding and path filters) and the results it gave. Jest's search names the files only for a run that lost some, because it knows the config's files and not a narrowing of them: asked every run, it throws under -o and reads every file of a shard as lost.
- A heap-snapshot reachability check reads instances by class name, and a subclass puts its parent prototype on the heap under the parent name, so assert on a class nothing extends, or hold a control of that same class.
- A heap-snapshot reachability check reads its snapshot a macrotask after the work it asks about, which the retainer helper does by yielding first: inside the work's own macrotask a `(Handle scope)` root can reach what the work's closures captured, and it shows on a CI runner and not locally. Filtering that root out would also hide a real path that begins at the test's own locals.
- A test reads a session's render events as one per render its client kept: the attempts the render helper's retry loop asked again after (a timeout, or an answer that drew a source pending at its deadline) are dropped by the same predicate the loop decides with, so an exact list of a session's events is a list of its renders. A request sent some other way, with no retry, would have such an answer hidden.
- A test that is not about the launcher's adapter scripts its programs on a fake spawner under the real launcher, so the timeout, abort, output bound, rate limit and owner's gate are the production code run on a held clock. A program nobody registered fails to start, so nothing succeeds by default. The fake child's stream events finish on the next-tick queue, which a chain of resolved promises never leaves room for: a held-clock case yields through that queue after each advance. A source left reading keeps its launch timeout armed until its registry is disposed, so the case disposes it.
- A test's click reads its session's context from the rig's book, as the host hands it. A verb's handler taken straight from the verb table skips that, and its click reads as one from a session that never rendered.
- The src lint rules that read types parse through the project, which cannot see a file that is not on disk: linting text at a made-up path fails to parse, and every rule's message is lost with it. A fixture of a rule that reads no types lints its probe paths with those rules off; a fixture of one that does lints its text at a file the project holds.
- A test's clock is built as the process's is, over timers that report what a task throws. A case's clock rethrows, so an unexpected throw fails it; a daemon takes only a reporting clock, so a daemon's case builds one, and a task's throw then reaches the bar. A task's owner writes no log line for its throw: the daemon logs it, once a hold. A detached task's throw never reaches the code that detached it, so a case reads it from the clock's reports.
- Code a dev tool and a test share lives outside the test suite, and takes what the suite binds as arguments: the session environment, the shell a daemon runs under, and how a daemon start acquires its slot. A test helper reads the worker's environment at import and registers its cleanups on the Jest file, so a tool that imported one would run on Jest's setup and fill the suite's machine-wide daemon pool. The tests acquire from the pool; a tool's start takes its slot at once. A daemon built in a worker swaps the worker's environment to the one it is given, so the worker's own goes in where that daemon starts, never into the shell a tool would share.
