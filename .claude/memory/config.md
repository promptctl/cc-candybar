# Config: resolution, the file as store, settings

## Resolution

Config locations form a chain. The user's XDG file loads first, followed by the approved project and local files. A working directory inside the project would repeat the project's file. Each layer merges over the ones below it and is validated with them, so an error names its own file. `--config PATH` selects the user layer. `--config-only PATH` loads the named file over the bundled defaults. When neither flag is present the host gets `CC_CANDYBAR_CONFIG` from the session's reported environment. Older clients send the resolved path as a hint.

Only ENOENT counts as absent. A location a stat can't see past, such as an unsearchable directory or a symlink loop, is reported and the search continues. An explicit path that doesn't exist renders the bundled default under a warning, never a silently empty config.

When `.json5` and `.json` sit side by side, `.json5` wins and the shadowed file gets a warning.

A project or local layer, and a repository's own plugin folder, load only once the user has approved that directory in the bar. A config can run commands, so a cloned repository asks once, as Claude Code does for a project's MCP servers. The answer is kept by repository directory, not by content, so editing the files never asks again, and a linked worktree answers under its main worktree's counterpart, so a new worktree never asks. The link is proven from the repository's side (the worktree is registered in the common git dir, and git's back-pointer there names this checkout's own `.git`), because a `.git` file is the gated directory's own claim and an untrusted directory can forge one or symlink another checkout's. A directory whose link can't be proven answers for itself. An older decision saved for a worktree applies there until the project has a decision. A project approval or decline takes precedence in every verified linked worktree. An entry whose directory is gone stays, because a missing directory proves nothing about which repository it was in. The host uses the same decision for project layers, write destinations and plugin definitions. It lists plugin names once to decide whether to ask and opens definitions after approval. If the listing fails, the host reports it once and applies the saved decision when the directory becomes readable. The host reads decisions from `repo-configs/repo-configs.json` under the state directory. The loose `repo-configs.json` from older installs supplies decisions while the current file is missing. An explicit answer carries those decisions forward and archives the older copy outside discovery. All layered renderers that used these files follow their changes.

A repository's plugins, from its plugin folder or listed by its own config, sit in their own namespace beside installed ones, because a repo folder named like an installed plugin would otherwise replace it for every session in that repo and break the user's placements of it. A config's plugins are the repository's when the chain found the file at the project's directory, never by the file's name, because an explicit config can carry a repository's file name. Within one namespace the nearer root still wins, and a name missing from one namespace is never looked up in the other. A definition names itself scope-free and the loader binds that name to its namespace at load, because one file loads from a repository and, once installed, from the user's root. A config file declares nothing under a plugin root except retuning a plugin's segment by field, because a name there shadows a plugin's; a segment, action or helper named just the root sits beside them, but a variable of that name shadows the payload's sources.

A placement under a plugin namespace the session doesn't render is data, like a false `when`, because a home config places a repository's cells for every repository it is used in. Only a placement under a plugin that does render, naming a segment it lacks, is broken state; its error names the definition that won and what it declares, since that is what the fix needs. Presence is judged against the chain's own plugins, a repository's included: judging against installed ones alone would make a typo in a repo cell vanish silently.

User files merge over the bundled default by name. Segments and presets merge by name and then by field, so a user declares only what differs. Root rows merge by name, and a whole tree replaces every row.

A layer adds a cell to a row it doesn't own by anchoring on a placement id, because that address means the same thing whether the row below was written as a rows map or as a whole tree. The loader places every layer's cells once, into the config's root and into the tree of each preset that restages, before any check or synthesis walks a tree, because a preset's whole tree replaces the config's root: cells applied to the root alone vanish under it, and clash with a preset that already places them. The merged config keeps no cells to place, because a later pass that placed them again would bring back a cell the load dropped. For the same reason every restaging preset then carries the tree it was judged as, whole: a rows map left as written merges again over the root that now holds the cells, and renders a tree no placement judged. A missing anchor is a warning, not an error, so a repository's guess about a user's layout can't break their bar; so is any issue only a cell brings, found by judging the chain again without cells and then taking them one at a time, so the warning names the insert entry rather than whatever key the check happened to report. It warns only for a root or preset a config file writes: the bundled ones lack most anchors by design, so its miss is like a false `when`, and warning there would put a standing ⚠ on every bar a repository adds to. An inserted cell carries the file that placed it, so edit mode offers it no click: it is an insert entry, and clicks rewrite only roots, even in the user's own file.

JSON5 tolerates duplicate keys (the last one wins), but the file editor refuses the whole document. So loading runs the editor's own scanner and warns. With one detector, the warning and the refusal can't disagree.

## Names never nest

No variable is declared under another. The draw lands a read on the first declared name it reaches and the load's walks on the longest, so the two agree only when nothing nests. The check runs over the names after every synthesis pass, because synthesized names are built from authored ones: a user variable `theme` is refused because the settings menu declares `theme.effective`, and a new synthesis that derives names from authored input can make a config that loaded stop loading.

## The config file is the durable store

There's no daemon-side overrides layer. A click that persists something edits the user's config file in place: it splices one value span and keeps every other byte, comments included. A value written by the menu looks the same as a hand-edited one.

The renderer never writes a file. A click's writes leave its turn as changes, each naming the settings it touches and the value it read there. The host plans the batch by directory entry, so edits through separate directory aliases compose on the same file. Separate hardlink names have separate entries. The host opens each destination and reuses discovery's cached text when the physical revision matches. It reads changed revisions through the same regular-file descriptor and treats only ENOENT as absence. The check is per setting, so a hand edit elsewhere in the file never refuses a click, and one to the same setting always does. A change is carried as JSON5 text, because a value carried as data would lose its comments and its layout. An object whose members can't be rebuilt byte for byte (an emptied `{}`) is changed whole, and nothing wider, so the check stays as narrow as the edit.

The host restores earlier files in reverse order if a publication fails. Shared discovery reobserves published or unrestored entries for every holder, including aliases. A complete restore needs no immediate targeted scan. The regular poll may still observe a changed file revision. The writer hears its refreshed config in the click's mailbox slot before the effect verdict. A successful batch applies what else the click did, including released picks and history. A failed batch keeps its draft and history and shows the reason on the ⚠.

When file events resume after a span the daemon couldn't vouch for, discovery runs again at every origin it follows, whatever each watch heard, because an edit made during the span may never have been heard. Only an origin whose snapshot digests anew is handed to the renderer, so the catch-up costs discovery's reads and loads only what moved.

A config snapshot is a fact about an origin, never a session's, so the renderer holds one per origin its last output named, and opens no file. An event that needs a snapshot it lacks waits under that origin until its config turn. A waiting context still takes its world state at once and only its view's opening waits, because the session's later world states queue behind it and the store refuses one older than it holds. A click proves its changes against the snapshot it holds and never discovers again before it acts: a hand edit the watch hasn't reached is caught by the per-setting read guard.

A config file, like every path the daemon watches by name (a `watch_file` file, the repository answers, HEAD and the index, a transcript), is polled: a periodic sweep reads each path where it is spelled, and opens no OS watch. On macOS a directory watch is an FSEvents stream over the directory's whole tree, with no depth, so one name watched in a repository root or in the home directory would route every build beneath it through fseventsd, which then wedges for the whole machine. A read at the path sees a write-then-rename as it sees an in-place write, because the new inode sits at the same path, and a path that does not exist yet is a read that fails until it does. A linked config, `watch_file`, transcript or settings file is polled at every hop of its chain of links, so an edit at the target is heard and re-pointing any link is a read that changes; a read walks a linked folder on the way, so re-pointing that is heard too. A path whose chain loops is reported, never dropped.

Only a folder watched whole (a plugin root, a `watch_file` folder) or as a tree (git's branch refs) is an OS watch. On Linux one binds the folder's inode, so a folder removed and made again at its path (a dotfiles re-stow) is deaf to the watch opened on the one before. Such a watch's key therefore names the folder's identity as well as its path, and a polled path's key names none, because a read at the path already sees a folder replaced on the way. A watched folder's own removal or replacement is reported under its own name (a rename on Linux, a change on macOS), and when the folder at the path is no longer the one the handle bound, the handle moves onto the folder made again, because every later event naming the folder is judged against the one it bound. A derive that finds a folder briefly gone keeps the watch it holds rather than trade it for one the OS refuses. A strict ancestor renamed away and another tree put at its path reports nothing to the handle; the period that judges every directory watch catches that (data-sources.md).

Which layer a click writes is a value on its action, so moving a write between layers is a config edit, never code. The click carries a concrete role: a save that asks binds the role as its link's value, as a picker binds an option, so no verb ever sees `ask`. A project or local write is refused without an approved project or in isolated config mode, because the session's chain then holds no such layer. A change names its layer by origin and role, never a path, and the host lands it in the file discovery last found for that role, so a renderer can't write a file its origin's chain doesn't hold. A local file the host creates is added to the repository's common `info/exclude` in the same landing, so it rolls back with the write and is excluded in every worktree. The host knows a local layer by its role, not its file name, because an explicit config can carry the local file's name. An answer to a repository's question is refused unless its directory is still its origin's repository, because the link was drawn for a repository the origin may have moved off since. A write's by-name reads (the row a placement sits in, the preset a save copies, a declaration a pin needs) look through what the file inherits: the loader's merge of the layers beneath it, unvalidated. A file above the user's inherits the user's layout, not the bundled one, and a chain with the written file taken out is no chain at all, so validating it refuses configs that load.

Every write first loads and validates the text it's about to write, and refuses it if it wouldn't load. It also refuses a change that a layer above the written one would hide, and names that layer.

Precedence, lowest to highest: bundled default < file < active preset < session pick < edit-mode staging.

## Settings are rows

Every globals field is one row of the fields table. The schema, the resolved globals, the menu control, the option domain, the payload field and the save format all derive from that row. A new setting is a row, the code that uses its value, and its tests. Controls are generated from the row's domain. A field no control fits is text-only. A field only the file sets has no control and no session pick; colour depth is one of these.

## Drafts, save, reset

A draft is derived, never flagged. It's a setting whose session value differs from what the file resolves to under the preset the save will land in. Save recomputes the drafts at click time against the config the session renders with, so it writes exactly what the button counted.

Save's write and the picks it releases land together, so no render draws the old file without the picks, a refused write keeps every draft, and a released session follows later changes to the file instead of pinning over them.

Every save releases every pick that is no draft against the config it wrote, so a save needs no case for a pick its setting can't hold: that pick is never written and never a draft. A save is the user deciding what the bar draws, so after one the bar keeps what was saved even when the stale pick's domain returns. Without a save the stale pick stays stored, so a reinstalled theme comes back.

A stale pick is not an unset one. The bar wears what lies beneath it and a ⚠ names it, but only when the pick decided the frame: a staged value above it, or a placement the frame doesn't draw, decides nothing. A `state` variable can't read a setting's key, because it would show the raw pick the setting reads as stale.

Reset deletes the setting at every layer: the globals, every bundled preset's globals, and every theme's default. A preset the user wrote keeps its pinned value, because that pin is the user's own content.

## Undo, and edit mode

Undo and redo work one step per click. A journal around every verb handler records each step, storing the whole file before and after for every file written. A step goes back as the changes between those two texts, so another session's write to a different setting of the same file doesn't stop it. A step whose setting no longer reads as it left it is refused loudly at the click, and that file drops off the session's stacks, since the step would be refused at every click that takes it. The text a step writes was loaded by nobody, so it passes the same loader gate as every other write. A write that fails for I/O keeps the step, to land once it can.

Edit mode holds a session draft with its own undo and redo. Preview uses the config the draft edits, and write availability follows the current host observation. Save merges the draft through the guarded writer, which can accept disjoint changes and leaves a conflicting draft open. Cancel drops the draft and its history.

## Placements

A segment declaration is a definition. Each node in a layout is a placement, identified by its id or, failing that, the segment name. Per-instance state is keyed on that id.

- A removal target or an anchor is a placement id, and it's checked only at click time. A load-time check would reject the config its own click wrote.
- An insertion mints its id at click time, over the rendered tree.
- Edit chrome is named by the placement and preset it serves, each spelled injectively, because a name keyed on walk position hands an open menu or list to a neighbour on every add, and the identifier collapse would merge names that differ only in punctuation.
- Configuring is a level inside arranging and is held in its own key, so configuring two placements at once can't be represented, and leaving edit mode by any control clears it.
- No variable may live under `settings`, because that name holds the placement's settings.
- Every placement has a theme setting and an effect setting without declaring them, and a segment that declares either is an error.
- If a helper reads a setting, the segment that calls it must declare that setting.
