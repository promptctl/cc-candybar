# Architecture: client, daemon, wire

## One shared host and named renderers

Claude Code’s statusline client sends the hook to the host and prints the reply. Worktrees can run different renderer builds against the same host. The host shares filesystem observations and watches across them. Each renderer owns its interpretation of those observations, including the last authorized config it could compile. A second build must be able to restart without dropping the first build’s watch or rereading its data. [LAW:one-source-of-truth]

The host admits input, executes effects and owns delivery confirmation. A renderer receives data and answers with data. Its diagnostics belong to the construction or turn that produced them. A completed terminal write can acknowledge the daemon warning it displayed even after the renderer has been replaced. The renderer’s presentation state belongs to the generation that drew the frame. [LAW:effects-at-boundaries]

The daemon speaks JSON lines over the renderer child’s standard input and output. The in-process renderer used by tests speaks the same contract. The setup preview uses the ordinary statusline client and daemon.

- The primary renderer runs the host’s executable entry. A worktree renderer runs its bound bundle. Both must speak the host’s private protocol.
- It is launched through the process's launcher, not the daemon's, because the daemon's close aborts its own launches before the renderer's close steps have run.
- It ends on its stdin's EOF, so it dies with a host killed with no cleanup; the launcher's lifeline is no part of that.
- While no renderer is live an input fails at once rather than starting one, because a request per tick that spawns would be a fork storm under a crash loop.

A request is answered by the frame its renderer presents. A request or feed keeps what its frame showed only when the host confirms it. The socket settles every receipt, including a buffered frame that was replaced and a write that threw. An exit that forgets leaks an otherwise unshown record. Surface layouts and shared session motion follow draw order, so a delayed receipt cannot restore an old view or rewind the animation clock.

The native statusline client can recover a cold host. It shows the session’s last good frame or a waiting indicator while the host starts. A timeout includes a command for inspecting the failure.

A one-shot Node subcommand folds its outcome into a plan (what goes to each stream, the exit code) and ends through one delivery that waits for both streams' write callbacks before exiting. A piped stdout flushes asynchronously on macOS, so an exit right after the write drops everything past the first 64 KiB the pipe buffered, and the loss is invisible on Linux, where pipes are synchronous. [LAW:single-enforcer]

## The wire is spelled in every runtime

The protocol lives in TypeScript and is copied into the Rust client as literal constants: version, frame cap and header, timeouts, error codes, diagnostic styling, and the code points the sanitizer neutralizes. The protocol check compares every copied constant across the runtimes, and a missing anchor counts as drift. Change a mirrored constant in both runtimes in one commit. When you add a mirrored constant, add a row to the check. The same check also covers the hint code both runtimes share, the vendored launcher's statusline push, which subcommands only the native client knows, and the one frame the Swift URL handler spells.

The host reads the link key on first use and holds it for terminal frame publication and click admission. The renderer declares typed action targets in the frame. The request and feed encoders both publish them with the host key, so a click from either surface takes the same admission path. A failed key read is retried at the next use, so removing the broken file recovers without restarting the daemon.

The URL handler's frame carries its own version, never the protocol version. The handler is resident and ships with the platform package, so it outlives daemon upgrades, and a daemon that refused an old frame version would lose every click until the user reinstalled. The daemon accepts every frame version it has ever shipped.

## The daemon is detached: session facts come from the client

A statusline client identifies the environment Claude Code gave it with a SHA-256 digest. Each tick sends the session, the hook, the current terminal dimensions and the client identity. When the host has no matching digest for that session, it requests the values before drawing. The client supplies them once within the same deadline. The host derives SSH, tmux, terminal capabilities, config selection and the Claude Code directory from that snapshot. Changing a variable takes effect on the next tick. Restarting the host or evicting the session causes a fresh request for the values.

Both shipped clients also speak the original v3 render form. An older daemon's unknown-kind reply triggers one full render with the original hints. An older client can still send those hints to the new host. The host saves the config origin and Claude Code directory across restarts. Pane and terminal observations live until the session leaves memory because tmux can assign a closed pane's ID to another pane. Daemon stats count the requests that needed the full snapshot before drawing.

The host keeps each client's reported environment in memory and adds its session facts when running configured sources and actions. A session-scoped clipboard or editor click and both steps of typing a slash command use that environment and the working directory reported by the same session. A desktop link carrying no session, or an older desktop link used before its session reports again, uses the host's desktop environment. A configured program needs the session's reported environment. Shared git and PR reads use the host's environment for the directory, less what the launcher withholds. The environment stays inside the host because it can carry keys and tokens.

The temptation: the daemon's `process.env` has `CLAUDE_CONFIG_DIR` right there, and reading it works on your machine. But it answers for whichever session spawned the daemon and is wrong for every other session.

A hint has three wire states: absent (a client too old to report it), null (it doesn't apply, e.g. not in tmux), and a value. Keep the three apart. If absent collapses into null, an old client's silence reads as a fact.

The client makes a relative path in a hint absolute against its own cwd. The daemon accepts only absolute paths.

## Identity and lifetime

There is one daemon per user, guarded by a pid file in the state directory. The socket path comes from the UID under /tmp, not from the state directory, so overriding XDG_STATE_HOME does not isolate the socket. A separate env override isolates it for tests and dev.

Restarts are normal, and every cache rebuilds cold. There is no idle or age shutdown, because either one would interrupt an active session. The only hard limit is the memory backstop (daemon-memory.md). The daemon also ends itself when the bundle it runs from, or the install's record of which bundle that is, changes or disappears, so a rebuild or an install takes effect without a manual restart.

A waited launch keeps a bounded capture per stream and ends the child past the bound, because a child that writes without end grows the capture string until V8 throws inside the data listener, and the uncaught exception takes the daemon down. The result then names the limit as its error while its streams hold the first bytes of the flood, so a message built from a failed launch takes the error before the program's own words. A blocking launch has only Node's own buffer limit.

A child the daemon launches without blocking on it dies with the daemon, however the daemon ends. A SIGKILL runs no cleanup in the dying process, so the end comes from a second process, the lifeline, which reads a pipe only the launcher holds and, at EOF, signals every child group still in flight.


## The daemon is a value inside a process

The daemon is built by the process that serves it, never at import, because every subcommand imports the entry. Everything a process owns (signals, the socket, the lease, the exit) stays in the shell over it, so a test can run the daemon's own request handling in a jest worker. A connection is not among them: the request backstop, a half-close and a subscription run over any stream, and the listener only hands one a socket. So the connection states its own half-close rule, because a rule left to the listener's option is one a stream built any other way would have to repeat. The shell and a test tear down by one close: a second teardown would be a second list of what the daemon holds, and a process's exit hides whatever that list misses. The close resolves once its steps have run, and the host's stores flush in the last of them, so whatever ends a daemon awaits it before the next daemon reads their files. The renderer holds no file to flush: the host keeps every store and writes each behind the renderer's store writes. Shutdown seals every renderer link and drains the journals and views only of links that retain a live renderer. Booting and down links still close, and no renderer starts during the drain. The supervisor settles inputs still waiting for boot with the closing outcome when shutdown cancels it.

Entering the drain seals request admission, ends render waits, and seals admission to external acts, including at the head of each pane queue. Work already in flight can finish through the journal barrier. That barrier then ends the launcher.

After a close nothing launches, no timer stays armed, and only the log is written; a read already under way may finish. A connection is the exception, because the daemon holds no list of them: a close leaves its stream open. A request's backstop still ends it, while a subscriber's has no backstop and stays open with nothing feeding it. So ending connections is the shell's, in a process by its exit and in a jest worker by the harness's stop. Launches end at one checkpoint in the launcher rather than in each owner, because a git pass or a multi-step lane setup folds a killed child into a field and goes on to the next launch, which an owner-by-owner close never sees. A launch carries its owner: a daemon's work holds that daemon's launcher, with its rate limits, its children and its lifeline, so a closed daemon's launches stay refused whichever daemon is live by then. The owner is threaded rather than carried by async context, which would put an async hook on the render path on Node 20 and 22. Each daemon holds its own action gates, built by the root, so two daemons in one process share no keyspace. A line logged after a close has finished says so, because that file can be the next daemon's log: each daemon has its own log object, and two of them share a file by path alone. A process exits with its close, so only a daemon closed in a process that goes on writes one. Session state stops persisting at close instead of refusing writes, because a render that was awaiting still has to land somewhere, and it must not land over the file a next daemon has taken up.

Time is a value a process hands down, like the host: the real clock, the timer globals and the loop's turn are read in one file, and a lint rule fails any other that reads them. The daemon holds two timekeepers. Its own, which a test holds by hand, times everything the daemon builds. The machine's, which the process main builds beside its host, times what the adapters build and what a client runs on: real children, real files and the log's blocking wait live in real time, so a held daemon must not freeze them. The two share one type, so the single place that holds both (the adapters' assembly) is where a swap would typecheck. A clock is built only over a reporter of what its tasks throw, and only the process world builds one over the machine's bare timers, so no task runs where its throw is lost. A task is named, because the daemon's reporter holds one error per name on every bar: what a task throws while its error is held is only counted, and when the hold ends the latest cause shows and is logged with that count, so a task throwing on every period, whatever it says, moves bars and the log once a hold. The subject goes in the name and nowhere else: a throw rewrapped to name its subject hides its cause behind a constant message.

A process reads its environment, home directory and temporary directory in one place, into a host value its main hands down; no other module reads them, and a lint rule fails one that tries. The daemon's paths, the places the user's config and plugins live, and its adapters are parsed from that host. That environment may name the repository of whichever shell spawned the daemon, and only the launcher's children are kept from those names, so a read in the daemon's own process must never take a repository from it. A path read from the environment at write time would be honoured by half the daemon and split the state directory with nothing to say so, which is why the daemon's modules take the one path they write to. A launch states only the variables it changes over the inherited ones, and an entry set to null removes one: an undefined value is a key JSON drops, so across a process it would leave the inherited value in place. The debug channel's switch is the one process-wide setting: each main sets it once from its environment, and it is off until then.

## Logs and stats

A click is the person's decision, so no deadline the daemon keeps removes one: a click the daemon has read runs however long its turn takes, unless its client, which waited for the answer, has hung up before its turn (no one is left to answer, and that client was told the outcome is unknown), and two clicks run twice. A TIMEOUT to a click request means no complete frame of it was read before the request guard answered, so its action did not run and it can be sent again. The guard answers on the loop turn after its timer, because a busy daemon runs its expired timers before it reads the sockets that filled meanwhile, and a click already waiting on its socket would otherwise be answered TIMEOUT for the daemon's own delay. A read click is answered with its own outcome, because a guard bounding it would make TIMEOUT mean "ran or was refused" and leave every reader to guess. The client's own clock is then the one that can cut the wait, and what it tells the reader is that the outcome is unknown. The guard bounds only the wait for a complete frame: once a url frame is read its click is under no deadline either, since its writer waits for no answer, or waits on the click only as long as its own clock allows, but a url frame the guard answered before it was read has its click refused.

Every render request writes exactly one render event, and every click request one click event. Fields are added stage by stage as the request goes through, so an absent field means the request stopped before that stage, and `-` means none. A session id is recorded only once it passes the session-id checkpoint, and a click's verb only once the daemon knows it, because nothing an untrusted request says is recorded as fact: a refused request's own words appear only in its problems. Any value a client could shape into something that parses as several fields (a session id, for example) is written as a JSON string. When a change introduces a new fact, put it on that event or on its source's refresh event. Counters go in the stats snapshot.

Each source logs what its failures say, once per refresh, and the payload repeats none of that text. A throw that escapes a refresh is the clock's, logged as a task's throws are, once a hold. The render event does name each source whose reading failed, or whose key failed before ever answering, by its variable on every render while it stands (a fault in a policy that has already answered shows as the variable's refresh warning instead), because the host's line names a run only by its digest, and nothing else ties a failure to the variable a bar draws. Every source records its refreshes in one ledger, which is what the stats and a feed's summary read. A refresh that is a unit of work writes its own line. A session lane's refresh is a step of its transcript entry's refresh, which is the one line, so a lane writes its own only when it fails; a lane that never lands holds its entry's refresh, whose line is then the one missing. A transcript write costs one line however many lanes read, and the backstop period's clean read costs none: a held session would otherwise add a line every period for as long as it sits quiet. It still counts in the ledger, and a failed one still writes.

The log never writes on the event loop. A synchronous write held every waiting client past its budget whenever the disk was slow, and each client that gave up was one more line. Lines still waiting when the process exits are written synchronously, so the death line lands. Anything reading the log, tests included, waits for the lines it expects rather than reading once.

A state file that does not read is never written over: the write planned from that read first renames the file its bytes sit in beside itself and starts from empty. For a symlinked file that is the link's target, because a write through the link would replace the target, not the link. So its bytes are kept for whoever wants them and saving resumes with nobody acting. Only a file that can be neither read nor renamed stops its store's saving, and the bar says so for as long as the daemon runs.

Nothing watches the state directory itself, because the log writes there on every request and on macOS every write to a watched directory is a file event the OS has to deliver. A file the daemon must see edited (the repository answers, which a user may edit by hand) is polled at its path, which opens no watch on the folder.

## Packaging and install

The npm package ships the bundle and a committed node shim. It has no lifecycle scripts, so it works the moment any package manager unpacks it. Per-platform optional packages carry the native binary. Install decides the fast path: it stages the native binary (or announces the shim where a platform has none) beside the bundle at a stable per-platform path, and writes that path into Claude Code's settings as the statusline command. In a source checkout the native build puts its binary at its own gitignored path, so the committed shim and the native build never fight over one file.

Install records its bundle in the state directory, and that record is the only thing either client reads to start a cold host: a client starts the recorded bundle, never its own, because a worktree's client would otherwise move every other session's bar. The install records the bundle it staged only when it wrote the statusline command or the command it kept runs the staged entry (a wrapper, `env`, `node`), and a checkout's deploy records itself only when that command runs it, so building or deploying a worktree leaves the record alone. The install uses the fact it holds rather than reading the command back, because a command can be any shell text and the words alone cannot always say which bundle runs. A checkout's deploy has no such fact, so it compares real paths for exact equality, never a path prefix, because a worktree can sit inside a checkout. No record or an unusable one refuses the spawn before the lock and cooldown, so it forks nothing and shows on the bar every tick; an install that predates the record has to run the install again. The host's binary watch includes the record, so repointing it ends the running host.

A source checkout is an install only when the statusline command names a path inside it; the bar then draws that checkout's own bundle, whatever origin or the registry hold. Install run from a checkout does not make it one: a rebuild in the checkout never reaches the copy Install stages. A checkout parked at an old commit draws old code and nothing says so, because its bundle matches its tree. The temptation, after a merge: "it's published, so the bar will pick it up." Publishing changes nothing on a screen a checkout draws; moving the checkout and rebuilding does.

pnpm settings live in the workspace YAML, because pnpm 11 ignores the `pnpm` field of package.json.

On macOS, install assembles a URL-handler app for the `cc-candybar://` scheme around a prebuilt Swift binary from the darwin platform package (a checkout builds its own), and copies the runtime to a stable path outside the pnpm store. The app is a resident forwarder: it writes the raw link, as one frame, to the socket of the daemon that signed it (its own daemon's default socket unless the link names another), and the daemon does all the parsing but which daemon signed the link. The daemon answers the frame with its verdict on the link (whether its signature opened) as soon as it reads it, and runs the click after: the app waits for the verdict, not the click (except for a frame that asks for acts on the desktop, below), so a slow click that lands is never told as failed, and a refused link becomes a notification at once. An older app hangs up without reading, so its verdict goes to no one. It never starts a daemon, because that would need the node and bundle paths, which age; a click on a dead daemon is lost, and the statusline's next tick restarts the daemon. A bar drawn over ssh is signed by the remote's daemon, while the click opens on the machine the terminal is on. Every signed link names the key that signed it, as a short one-way id in the first field of its proof, and the user's ssh forwards the remote's socket to a file named by that id in a directory under the home (the remote prints the config lines). The app opens the one socket the link names, or its own daemon's when no forward by that name exists, and that daemon says which daemon signed the link. The id routes and the mac still authenticates. The remote's forward-config command asks the running daemon for the id instead of reading the key file, because the daemon is detached and keeps the key it loaded, wherever its environment pointed; a file read in the user's shell can name a key nothing signs with. Routing names the signer, not the host, because the remote cannot know the alias the user's ssh config reaches it by, but it knows its key, which two machines never share and which does not change when a machine is renamed. The alias is the one thing the user supplies, once: it is the `Host` line of the printed stanza, and ssh's own `%n` writes it into the forward's file name after the key, because that name is all the app reads of a forward and an editor needs the alias to reach the remote's files. Trying each socket in turn instead fails three ways: a dead forward ends the search before the owner is reached, the link (a copy link carries its text) goes to machines that did not draw it, and the notice names a refusal that was only routing. A copy or open click that arrived down a forward acts on the person's machine, the only one with their clipboard and editor, so every frame says where its acts go (the desktop down a forward, the daemon otherwise; absent reads as the daemon, for an older app), and a frame that says the desktop gets its verdict after the click lands, carrying the acts, so the app's wait bounds how long such a click may take. A session click carries the origin's snapshot when the host has not delivered it yet. The renderer processes it in the writer's own turn, so the reply can carry its acts even on the first click after a restart. The remote daemon checks whether an editor target is a file or directory on its filesystem. Acts handed to the desktop leave with the click however it ended, since a click that fails after asking still asked. Its failure rides in that same verdict, whether or not it asked any act, because a failed response means the daemon could not take or answer the click: the app tells its reason as the daemon's, and blames the ssh forward only when the frame never reached the daemon. Acts handed to the desktop skip the launcher's per-second limit on click helpers, which guards the daemon's own spawns. A verdict with no acts for a frame that asked is an older daemon, which did the click on its own machine, and the app says so instead of reading it as success. The app is background-only, not an agent: Launch Services activates an agent to deliver a link, and a resident app keeps that focus, so each click would take keyboard focus from the user's terminal and break the settings menu. A short-lived app hid this, because focus returns to the previous app when it quits. Launch Services never relaunches a running app, so install quits the resident instance before registering the new bundle. The `url-handle` subcommand sends a link to the daemon by hand.
